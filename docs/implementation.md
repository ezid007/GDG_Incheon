# 골목탐정 구현·협업 안내

확인 날짜: 2026-09-12 · 적용 버전: `field-v2` · 서비스: 차이나타운 골목탐정

## 현재 목표와 범위

**한 장소에서 ‘1차 장소 찾기 → 2차 현장 4지선다’를 이어서 체험하는 모바일 탐험 게임**입니다. 1차에서는 그림 지도와 크롭 사진을 보고 장소를 찾고, 2차에서는 현장에 있는 관찰 대상에서 답을 확인합니다. 장소 찾기와 현장 퀴즈를 서로 다른 장소의 미션으로 계산하지 않습니다.

현재 콘텐츠는 **인화문 현판을 묻는 실제 4지선다 미션 1개와 보존한 가상 예시 SVG 3개**입니다. 일반 첫 화면은 실제 미션만 소개하며 탐색 지도로 이동합니다. 예시는 실제 문제가 없는 구역의 시연에서 대체 자료로 사용합니다.

팀원이 공유한 `python/quiz_class_sample.py`와 당시의 `raw/missions/`·`wiki/` 자료를 확인해 실제 미션을 반영했습니다. 폴더 정리 후 과거 원본은 [커밋 096c7fc](https://github.com/ezid007/GDG_Incheon/tree/096c7fc)의 기록으로 남으며 게임은 검수한 `public/assets/` 복사본을 사용합니다. `wiki/mission-chinatown-gate.md`의 초기 초안에는 다른 관문 이름이 있어 그대로 가져오지 않았습니다. 사진의 현판과 보기 4개를 대조한 결과와 사진 사용 시점은 [현장 미션 검수 기록](field-missions.md)에 있습니다. 추가 문제는 같은 검수 과정을 거쳐 반영합니다.

회원가입, 데이터베이스, GPS 도착 인증, 방문자 파일 업로드, 플레이 중 AI 호출은 포함하지 않습니다. 지도는 요청 시 현재 위치를 한 번 표시하지만 위치로 문제를 잠그지 않습니다. 정답 위치 핀 대신 넓은 탐색 구역을 보여주고 플레이어가 직접 다음 단계로 넘어갑니다.

## 사용자 흐름

| 단계 | 사용자 행동 | 서비스 동작 |
|---|---|---|
| 시작 | ‘1차 퀴즈 시작하기’ 선택 | 첫 실제 미션의 탐색 지도 표시 |
| 1차 · 장소 찾기 | 넓은 구역과 크롭 사진 힌트로 장소 찾기 | 지도·단서 사진 표시, 요청 시 대략적인 현재 위치 확인 |
| 단계 전환 | ‘장소를 찾았어요 → 2차 퀴즈’ 선택 | 해당 구역의 실제 현장 문제 표시 |
| 2차 · 현장 관찰 | 현장에서 답을 확인하고 4개 보기 중 선택 | 선택 상태와 관찰 힌트 표시 |
| 정답 확인 | ‘정답 확인’ 선택 | 오답은 재시도, 정답은 전체 확인 사진·근거·해설 표시 |
| 완료 | ‘탐험 결과 보기’ 선택 | 발견 기록과 다시 시작 제공 |

‘장소를 찾았어요’는 **사용자 스스로 다음 단계로 넘어가는 버튼**이며 GPS 인증이 아닙니다. 이 버튼이나 시연 링크가 정답을 자동 처리하지 않습니다. 2차 퀴즈에서는 정답 확인 전에 다음 문제로 넘어갈 수 없고, 정답을 맞힌 뒤 답을 바꾸거나 진행도를 중복 추가할 수 없습니다.

시작 화면·지도·선택·오답·힌트에서는 크롭된 단서 사진만 보여줍니다. 정답을 맞힌 뒤 전체 사진과 정답의 근거를 공개합니다. 정답 자료는 정적 배포 파일에 포함되므로 화면의 공개 시점을 구분하는 체험 게임의 용도입니다.

## 실행과 수정

검증 환경은 Node.js 22/24이며 외부 패키지를 설치하지 않습니다. 저장소 루트에서 실행합니다.

```sh
# 게임과 지도 생성
node apps/golmok-detective/build.mjs

# 기본 포트 4179에서 시작
node apps/golmok-detective/serve.mjs

# 필요한 경우 포트 변경
node apps/golmok-detective/serve.mjs --port 4180

# 전체 검사
node --test apps/golmok-detective/tests/*.test.mjs
```

[http://127.0.0.1:4179](http://127.0.0.1:4179)는 서버를 실행한 컴퓨터에서만 열립니다. 미션이나 코드를 수정한 뒤 다시 빌드하고 브라우저를 새로고침합니다. 서버는 요청할 때마다 현재 파일을 읽고 캐시를 남기지 않도록 응답합니다.

## 현장 미션 작성과 사진 공개

팀원은 [작성 양식](mission-authoring.md)에 질문, 사진, 고유 선택지 4개, 정답 1개, 실제 관찰 근거와 넓은 탐색 구역을 적습니다. 현장 미션에는 `sceneKind: "field"`와 `explorationRegionId: "chinatown"` 또는 `"songwol"`이 필요합니다. 기존 예시의 `sceneKind: "example"`은 3지선다를 유지합니다.

| 필드 | 작성 내용 |
|---|---|
| `id`, `sourceId` | 고유 미션 ID와 자료 출처 식별자 |
| `sceneKind`, `explorationRegionId` | 실제·예시 구분과 연결할 탐색 구역 |
| `placeLabel` | 정답을 미리 알려주지 않는 장소 설명 |
| `image`, `imageAlt` | 장소를 찾는 크롭 사진 경로와 정답을 드러내지 않는 설명 |
| `question` | 현장에서 관찰할 질문 |
| `options`, `answerId` | 고유 선택지 4개와 그중 하나인 정답 ID |
| `hint` | 실제 현장에서 볼 위치나 관찰 방법 |
| `answerImage`, `answerImageAlt` | 선택 사항인 정답 확인 사진과 필수 대체 설명 |
| `explanation`, `evidenceQuote` | 정답 이유와 실제 관찰 근거 |
| `evidence` | 최종 정답 확인 사진에서 근거를 표시할 0~100 백분율 좌표 |

`answerImage`를 제공하면 `answerImageAlt`도 작성합니다. 정답 확인 후 본문 사진·확대 사진·완료 썸네일에 해당 이미지를 사용합니다. 사진은 원본 비율로 표시하며 근거 마커는 전체 확인 사진 기준으로 배치합니다. 별도 확인 사진이 없으면 문제 사진에서 근거를 표시합니다.

이미지 경로는 검토된 `public/assets/` 파일을 사용하며 빌드 때 HTML에 내장합니다. 현재 현장 JPG는 게임·지도 HTML을 통해 표시하므로 로컬 서버에 별도 사진 경로를 추가할 필요가 없습니다. 원본 자료와 개인정보·개인 PC 경로를 그대로 공개 데이터로 옮기지 않습니다.

최상위 `version`은 저장 상태의 호환성을 구분합니다. 이번 실제 미션 반영에서 `example-v1`을 `field-v2`로 변경했습니다. 미션 순서·선택지·정답을 바꾸면 버전도 갱신하며 오래된 진행 상태는 초기화합니다. 현장 질문·정답이나 미확인 좌표를 임의로 만들지 않습니다.

## 모드와 진행 상태

| 진입 방식 | 보여주는 자료 | 시작 동작 |
|---|---|---|
| 일반 루트 `/` | 실제 미션이 있으면 실제 미션만 소개, 없으면 예시 | 실제 미션 시작 버튼은 첫 구역 지도로 이동 |
| `?play=field&region=chinatown` | 해당 구역의 실제 미션만 | 2차 퀴즈 자동 진입, 없으면 준비 중 화면 |
| `?demo=arrival&region=chinatown` | 해당 구역 실제 미션 우선, 없으면 예시 | 현장에 가지 않고 2차 퀴즈 시연, 시연 표시 유지 |

`region`은 `chinatown` 또는 `songwol`을 사용합니다. 유효하지 않거나 서로 충돌하는 모드 인수는 일반 시작으로 처리합니다. 일반 도착 모드에 문제가 없다고 다른 구역의 실제 문제나 예시를 연결하지 않습니다. 시연에서도 실제 문제와 예시가 모두 없으면 준비 중 화면을 보여줍니다.

일반 루트, 구역별 현장 플레이, 구역별 시연은 서로 다른 저장 키·버전을 사용합니다. 시연 결과는 일반 플레이 기록에 합쳐지지 않습니다. 공유 주소에는 해당 모드와 구역을 유지하며 같은 탭의 새로고침은 그 모드의 진행을 복원합니다. 기기 간 동기화는 없습니다. 저장이 차단되면 안내를 표시하고 메모리에서 계속 플레이합니다.

`game-state.mjs`의 `initialState`, `transition`, `restoreState`는 `start`, `mission`, `complete` 화면과 순서대로 해결한 미션 ID를 관리합니다. 저장 복원은 존재하지 않는 선택지, 중복·누락·순서가 어긋난 정답 기록, 서로 맞지 않는 정답·화면 상태를 거부합니다. 지도 1차 화면은 별도의 `map.html`이며 정답 판정 상태와 구분합니다.

## 지도·서버·외부 접속

지도는 실제 도로 데이터로 만든 그림 지도와 넓은 탐색 구역을 사용합니다. 현재 A 차이나타운 남쪽은 인화문 미션과 연결되고 B 동화마을은 문제 연결 준비용입니다. 정답 위치 핀과 GPS 도착 잠금은 없습니다. 자세한 지도 출처·표시 한계는 [지도 안내](map.md)에 있습니다.

‘내 위치 확인’은 사용자의 위치 권한 허용 후 현재 위치와 오차를 한 번 표시합니다. 서버에 전송하거나 저장하지 않습니다. 지도 밖, 큰 오차, 오래된 측정 결과는 안내만 표시하고 부정확한 점을 만들지 않습니다. 실제 현장의 GPS 정확도는 휴대전화에서 추가 확인해야 합니다.

기본 공개 주소는 [GitHub Pages](https://ezid007.github.io/GDG_Incheon/)이며 개발 노트북이 꺼져도 이용할 수 있습니다. [임시 HTTPS 주소](https://machines-ambien-wear-arab.trycloudflare.com/)는 개발 노트북·서버·터널·네트워크가 유지되는 동안의 수정 확인용입니다. 운영과 배포는 [공개 운영 안내](deployment.md)를 따릅니다.

로컬 서버는 `127.0.0.1:4179`에서 `index.html`, `map.html`과 예시 SVG 3개만 GET·HEAD로 제공합니다. 다른 경로는 404이며 문서·로그·환경 변수·첨부 원본 폴더를 제공하지 않습니다. 게임·지도 HTML에는 필요한 사진·SVG·코드가 내장되고 외부 지도 타일을 요청하지 않습니다. GitHub Pages는 배포한 `public/` 파일을 제공하므로 로컬 서버의 경로 제한과 구분합니다.

## 현재 검증과 남은 항목

2026-09-12 현재 `field-v2`의 검증 상태입니다. **이번 변경의 CI 실행·공개 배포 확인은 대기 중**입니다.

| 검사 | 현재 결과 | 범위 |
|---|---|---|
| 로컬 상태·지도·미션·세션 검사 | 59개 통과 | 상태 전환, 지도 표시·위치 처리, 데이터 검증, 모드·구역 선택과 저장 분리 |
| 서버 포함 전체 로컬 검사 | 68개 중 66개 통과, 2개 실패 | 실패는 기존 AdGuard의 HTML 응답 변경·HEAD 파싱 문제 |
| 실제 미션 브라우저 통합 | 통과 | 2차 정답 사진·완료·새로고침 복원, 시연 정답 후 복원과 일반 루트 분리, 320·390·1280px 게임·지도 가로 넘침 없음 |
| 이번 버전 GitHub Actions·공개 URL | 확인 대기 | 최신 커밋의 검사·빌드·배포 성공과 공개 화면 대조 필요 |
| 현장 휴대전화 | 추가 확인 필요 | 모바일 데이터망 접속, 현장 GPS 오차, 실제 보행 중 지도 사용 |

로컬 AdGuard는 HTML 응답의 `Content-Length`·CSP를 변경하고 HEAD 응답에서 chunked 파싱 오류를 일으킨 이력이 있습니다. 서버가 생성한 원래 GET·HEAD 헤더와 무본문 계약을 별도 검사해 원인을 구분합니다. 이번에도 해당 두 실패를 기록하며 테스트를 삭제·완화·건너뛰지 않습니다. 필터 설정은 변경하지 않았습니다.

### 초기 예시 버전의 검증 기록

다음은 **현재 실제 미션의 배포 증거가 아닌 이전 버전 기록**입니다.

- 최초 상태·서버 검사 20개는 로컬에서 18개 통과·AdGuard 관련 2개 실패였고, GitHub Actions Ubuntu/Node 24에서는 20개 모두 통과했습니다([초기 실행](https://github.com/ezid007/GDG_Incheon/actions/runs/34669308422)).
- 지도 공개 경로 검사 추가 후 GitHub Actions에서 21개 모두 통과했습니다.
- 예시 3미션 완주, 오답 재시도, 힌트, 확대, 저장 복원, 재시작, 주소 복사를 브라우저에서 확인했습니다.
- 320·390·768·1280px 가로 넘침과 깨진 이미지를 확인하고, 공개 HTTPS GET·HEAD 및 비공개 경로 404를 확인했습니다.
- 이름 변경 시 320px에서 긴 제목이 잘리지 않도록 헤더 높이·여백을 조정했습니다.

## 협업과 발표 준비

현장 담당은 단서 사진과 전체 확인 사진을 구분하고, 문제 담당은 4개 보기와 정답 근거를 검수합니다. 제작 담당은 자료를 반영한 뒤 1차 탐색부터 2차 퀴즈·완료까지 확인합니다. 추가 미션은 준비가 끝난 구역부터 연결하며 기존 초안이나 원본 자료를 임의로 덮어쓰지 않습니다.

발표에서는 ‘지도와 사진으로 찾아가기 → 현장 관찰 → 정답 근거 확인’을 먼저 설명합니다. 현장에 없는 발표자는 별도 시연 링크로 2차 퀴즈를 보여줄 수 있습니다. 사람과 Agent가 맡은 역할, 현장 관찰을 통해 확인·수정한 내용을 함께 기록합니다.

2차 문제 사진은 `quizImage`·`quizImageAlt`로 지정한다. 게임 본문과 확대 화면의 정답 전 사진은 이 파일을 사용하고, 시작 화면·탐색 지도는 `image`의 부분 사진을 유지한다. `quizImage`가 없으면 기존 방식과 호환되도록 `image`를 사용한다. 두 사진 필드는 대체 설명과 쌍으로 검증하며 빌드에 내장한다.

## 팀원 문제 소스 통합

팀원의 정리 커밋에 따라 `missions.json`은 사용하지 않는다. `load-quiz.mjs`는 `quiz.js`의 질문·선택지·좌표를 읽고 `quiz-support.json`의 검수 정보(단서/문제/정답 사진 설명·해설·근거 좌표·검수 정답)와 결합한다. 팀원 형식의 `correctAnswerIndex`는 1부터 시작하는 보기 번호로 해석하고, 해당 보기의 글자가 검수 정답과 같은지 확인한다. 원본 세 사진과 공개 복사본이 다르거나 새 문제가 아직 검수 목록에 없으면 빌드를 중단한다. 사진 이름만으로 힌트 공개 여부를 결정하지 않는다.
