# 골목탐정 구현·협업 안내

## 공유 창의 QR과 주소 복사 · 2026-09-13

상단의 `링크 공유`와 완료 화면의 공유 버튼은 같은 창을 엽니다. 창에는 제공받은 QR 원본, 스캔 안내, 게임 첫 화면 주소, `주소 복사하기` 버튼이 함께 표시됩니다. 기존에는 링크 미리보기용 메타 정보만 추가되어 공유 창 본문에 QR이 없었으므로 본문 표시를 보완했습니다.

`build.mjs`가 `assets/share-qr-20260913.jpg`를 HTML 자산에 포함하고 `share()`가 이미지에 연결합니다. QR 원본과 기존 중간 서비스 연결은 유지하며, 문제·시연 쿼리는 복사 주소에서 제외합니다. 정사각형 이미지와 흰 여백을 유지하고 작은 화면에서는 복사 버튼을 전체 너비로 표시합니다. 창 높이는 화면 안으로 제한하고 필요한 경우 내부를 스크롤할 수 있습니다. 새 패키지는 없습니다.

검증: 빌드 성공, 전체 76개 검사 통과. 320·390px 모바일과 1280px 화면에서 QR·주소·버튼 표시 확인. 복사 성공 안내, 닫기 버튼, Escape 닫기와 공유 버튼으로 초점 복귀, QR 원본 크기 1280×1280 로딩과 브라우저 오류 없음 확인. 공개 반영 결과는 작업 계획의 완료 기록을 따릅니다.

## 현재 통합 상태 · 2026-09-13

버전 `unified-three-missions-v1`. main의 첫 안내·기본 공유 URL과 refactoring의 단일 JSON·사진 폴더·스키마 및 동화마을 문제를 병합했습니다. 실제 문제는 인화문·피노키오·동화마을 3개입니다. 아래의 2026-09-12 상태와 quiz.js/복사본 파이프라인 설명은 당시 이력이며 현재 설정은 [작성 안내](mission-authoring.md)를 따릅니다.

콘텐츠는 `data/quiz-support.json`, 사진은 `public/assets/quiz/{gate,pinocchio,taletown}/`에 있습니다. 스키마 클래스는 검증에 사용하고 로더 경계에서 structuredClone으로 일반 객체를 반환합니다. 기존 비변경 검사를 유지하면서 클래스 prototype 때문에 생긴 실패를 해결했습니다. 파일을 읽기 전에 미션·이미지 경로 검증을 수행하고, 중복 검수 키와 모호한 정답을 거부합니다. 타입 선언도 검수 입력(expectedAnswer)과 런타임 출력(answerId)을 구분합니다.

생성 HTML 충돌은 양쪽 소스를 통합한 뒤 build.mjs로 해결했습니다. 75개 중 73개 검사 통과, 기존 AdGuard HTTP 2실패 유지. 320/390px 목록·이미지, 첫 안내와 시연/일반 기록 분리, 동화마을 오답→가방 정답→완료→목록 복귀를 확인했습니다. 1280px은 DOM 가로 치수를 확인했습니다. GitHub Pages 게시 중단·워크플로 비활성 상태를 유지해 이번 CI/배포는 실행하지 않습니다.

동화마을 사진은 양철 나무꾼과 성 외관이므로 설명을 바로잡았습니다. 정답은 출제자의 가방을 보존합니다. 별도 정답 사진이 없는 현장 문제는 참고 사진에 근거 표시점을 찍지 않습니다. 벽화 전체 근거 사진과 현장 GPS 확인은 남아 있습니다.

## 현재 목표와 범위

**공용 지도1개와 모든 실제 문제의 세로 카드 목록으로 ‘1차 장소 찾기 → 2차 현장 4지선다’를 체험하는 모바일 게임**입니다. 지역 탭과 가로 문제 전환 탭을 사용하지 않고 아래로 스크롤하며 문제1·문제2를 봅니다. 각 카드에 장소 찾기 사진·안내·도착·시연 버튼을 두며, 실제 퀴즈 화면도 사진 다음에 질문·보기가 세로로 이어집니다. 장소 찾기와 현장 퀴즈는 한 문제의 두 단계입니다.

현재 콘텐츠는 **인화문과 피노키오의 실제4지선다 문제2개, 보존한 가상 예시3개**입니다. 실제 세로 목록에는 문제2개만 넣습니다. 피노키오 사진은 사용자 최종 지시대로 `최초 Photo1 피노키오·하트 크롭으로 찾기 → 최초 Photo3 파란 무늬 확대로2차 퀴즈 → 최신 사용자 확인 벽면 사진으로 정답 확인` 순서입니다. 이전 파란 무늬 우선 배치는 대체했으며 인화문 출제 내용과 파란 계열5개 정답은 유지합니다.

팀원이 공유한 `python/quiz_class_sample.py`와 당시의 `raw/missions/`·`wiki/` 자료를 확인해 실제 미션을 반영했습니다. 폴더 정리 후 과거 원본은 [커밋 096c7fc](https://github.com/ezid007/GDG_Incheon/tree/096c7fc)의 기록으로 남으며 게임은 검수한 `public/assets/` 복사본을 사용합니다. `wiki/mission-chinatown-gate.md`의 초기 초안에는 다른 관문 이름이 있어 그대로 가져오지 않았습니다. 사진의 현판과 보기 4개를 대조한 결과와 사진 사용 시점은 [현장 미션 검수 기록](field-missions.md)에 있습니다. 추가 문제는 같은 검수 과정을 거쳐 반영합니다.

회원가입, 데이터베이스, GPS 도착 인증, 방문자 파일 업로드, 플레이 중 AI 호출은 포함하지 않습니다. 지도는 요청 시 현재 위치를 한 번 표시하지만 위치로 문제를 잠그지 않습니다. 정답 위치 핀 대신 넓은 탐색 구역을 보여주고 플레이어가 직접 다음 단계로 넘어갑니다.

## 사용자 흐름

| 단계 | 사용자 행동 | 서비스 동작 |
|---|---|---|
| 문제 살펴보기 | 세로 카드 목록을 아래로 스크롤 | 실제 문제2개를 모두 표시, 가로 전환 탭 없음 |
| 1차 · 장소 찾기 | 공용 지도와 해당 카드 사진으로 장소 찾기 | 공용 지도1개, 카드별 넓은 범위·사진·안내, 요청 시 위치 확인 |
| 단계 전환 | 해당 카드의 ‘장소를 찾았어요 → 2차 퀴즈’ 선택 | 같은 문제의2차 사진·4지선다를 세로로 표시 |
| 2차 · 현장 관찰 | 현장에서 답을 확인하고 4개 보기 중 선택 | 선택 상태와 관찰 힌트 표시 |
| 정답 확인 | ‘정답 확인’ 선택 | 오답은 재시도, 정답은 전체 확인 사진·근거·해설 표시 |
| 다음 문제 | 정답 해설 후 다음 문제 선택 | 다음 문제의 1차 장소 찾기 지도로 이동 |
| 목록으로 | 마지막 문제 완료 또는 문제 목록 선택 | 실제 문제 목록으로 돌아가 다른 문제를 선택 |

‘장소를 찾았어요’는 **사용자 스스로 다음 단계로 넘어가는 버튼**이며 GPS 인증이 아닙니다. 이 버튼이나 시연 링크가 정답을 자동 처리하지 않습니다. 선택한 문제의 2차 퀴즈에서는 정답을 맞힌 뒤 답을 바꾸거나 진행도를 중복 추가할 수 없습니다. 다음 문제로 진행할 때는 곧바로 답을 고르는 화면을 열지 않고 그 문제의 1차 지도를 거칩니다.

시작/장소 찾기 카드에는 `image`, 도착 후2차 질문·선택·오답·힌트·확대에는 `quizImage`, 정답 후에는 `answerImage`를 사용합니다. 사진과 질문을 좌우로 나누지 않고 세로로 배치합니다. 정답 자료는 정적 배포 파일에 포함되므로 화면의 공개 시점을 구분하는 체험 게임의 용도입니다.

| 문제 | 1차 장소 찾기 | 도착 후2차 | 정답 후 |
|---|---|---|---|
| 인화문 | 금빛 조각상 부분 사진 | 현판을 가린 사진 | 현판 글자가 보이는 전체 사진 |
| 피노키오 | 최초 Photo1 피노키오·하트 크롭 | 최초 Photo3 파란 구름 무늬 확대 | 사용자 확인을 받은 최신 벽면 사진 |

## 실행과 수정

검증 환경은 Node.js 22/24이며 외부 패키지를 설치하지 않습니다. 저장소 루트에서 실행합니다.

```sh
# 게임과 지도 생성
node apps/golmok-detective/build.mjs

# 기본 포트 4179에서 시작
node apps/golmok-detective/serve.mjs

# 필요한 경우 포트 변경
node apps/golmok-detective/serve.mjs --port 4180

# 전체 검사
node --test apps/golmok-detective/tests/*.test.mjs
```

[http://127.0.0.1:4179](http://127.0.0.1:4179)는 서버를 실행한 컴퓨터에서만 열립니다. 미션이나 코드를 수정한 뒤 다시 빌드하고 브라우저를 새로고침합니다. 서버는 요청할 때마다 현재 파일을 읽고 캐시를 남기지 않도록 응답합니다.

## 현장 미션 작성과 사진 공개

팀원은 [작성 양식](mission-authoring.md)에 질문, 사진, 고유 선택지 4개, 정답 1개, 실제 관찰 근거와 넓은 탐색 범위를 적습니다. 현장 미션의 `sceneKind: "field"`만 실제 문제 목록에 들어갑니다. `explorationRegionId`는 기존 대표 영역을 찾는 내부 지도 배치 정보이며 화면의 지역 탭이나 문제 필터가 아닙니다. 기존 예시의 `sceneKind: "example"`은 3지선다를 유지하되 실제 목록에서 제외합니다.

| 필드 | 작성 내용 |
|---|---|
| `id`, `sourceId` | 고유 미션 ID와 자료 출처 식별자 |
| `sceneKind`, `explorationRegionId` | 실제·예시 구분과 지도 배치용 기본 대표 영역 |
| `explorationArea` | 선택 항목 `{ latitude, longitude, radiusMeters }`. 이 문제의 검수한 넓은 탐색 범위를 지정하면 기본 대표 영역보다 우선 |
| `placeLabel` | 정답을 미리 알려주지 않는 장소 설명 |
| `image`, `imageAlt` | 장소를 찾는 크롭 사진 경로와 정답을 드러내지 않는 설명 |
| `quizImage`, `quizImageAlt` | 2차 현장 퀴즈 사진과 대체 설명. 인화문은 가림 사진, 피노키오는 파란 무늬 부분 확대 |
| `question` | 현장에서 관찰할 질문 |
| `options`, `answerId` | 고유 선택지 4개와 그중 하나인 정답 ID |
| `hint` | 실제 현장에서 볼 위치나 관찰 방법 |
| `answerImage`, `answerImageAlt` | 선택 사항인 정답 확인 사진과 필수 대체 설명 |
| `explanation`, `evidenceQuote` | 정답 이유와 실제 관찰 근거 |
| `evidence` | 최종 정답 확인 사진에서 근거를 표시할 0~100 백분율 좌표 |

`answerImage`를 제공하면 `answerImageAlt`도 작성합니다. 정답 확인 후 본문 사진·확대 사진·완료 썸네일에 해당 이미지를 사용합니다. 사진은 원본 비율로 표시하며 근거 마커는 전체 확인 사진 기준으로 배치합니다. 별도 확인 사진이 없으면 문제 사진에서 근거를 표시합니다.

이미지 경로는 검토된 `public/assets/` 파일을 사용하며 빌드 때 HTML에 내장합니다. 현재 현장 JPG는 게임·지도 HTML을 통해 표시하므로 로컬 서버에 별도 사진 경로를 추가할 필요가 없습니다. 원본 자료와 개인정보·개인 PC 경로를 그대로 공개 데이터로 옮기지 않습니다.

`data/quiz-support.json`의 최상위 `version`은 저장 상태의 호환성을 구분합니다. 이번 세로 카드와 사진 역할 변경에서는 `scroll-pinocchio-v1`을 사용합니다. 앞선 단일 지도 통합 `unified-v1`, 무늬 정정 `unified-pinocchio-v2`의 기록은 역사로 보존합니다. 미션 순서·선택지·정답이나 사진 역할·저장 방식이 바뀌면 버전을 갱신하며 오래된 진행 상태를 그대로 사용하지 않습니다.

| 일반 루트 `/` | 검수한 실제 문제의 세로 목록 | 카드에서 장소 찾기로 이동. 예시3개를 실제 목록에 넣지 않음 |
| `map.html?quiz=inhwamun-plaque` | 공용 지도와 실제 문제 카드 전체 | 해당 문제를 가리키는 링크를 유지하며 세로 스크롤로 다른 카드도 확인 |
| `?play=field&quiz=inhwamun-plaque` | 해당 ID의 실제 문제 하나 | 도착 후2차 사진·질문·4지선다를 세로로 표시 |
| `?demo=arrival&quiz=inhwamun-plaque` | 해당 ID의 실제 문제 하나 | 현장에 가지 않고 2차 퀴즈 시연, 시연 표시 유지 |

새 주소는 검수한 실제 문제의 ID를 `quiz`로 전달합니다. 예전 `region=chinatown` 또는 `region=songwol` 주소는 호환용으로 처리할 수 있지만, 새 UI·공유 링크의 선택 기준으로 지역을 쓰지 않습니다. 내부 대표 영역이 있다고 실제 문제가 자동 등록되는 것은 아닙니다. 등록되지 않은 문제나 보존 예시를 실제 문제 목록에 섞지 않습니다.

진행은 **문제 ID별·현장 플레이/시연별**로 저장합니다. 문제 1의 시연 결과가 문제 1의 실제 플레이나 문제 2의 기록에 합쳐지지 않습니다. 공유 주소에는 해당 모드와 문제 ID를 유지하며 같은 탭의 새로고침은 그 문제·모드의 진행을 복원합니다. 기기 간 동기화는 없습니다. 저장이 차단되면 안내를 표시하고 메모리에서 계속 플레이합니다.

`game-state.mjs`의 `initialState`, `transition`, `restoreState`는 `start`, `mission`, `complete` 화면과 순서대로 해결한 미션 ID를 관리합니다. 저장 복원은 존재하지 않는 선택지, 중복·누락·순서가 어긋난 정답 기록, 서로 맞지 않는 정답·화면 상태를 거부합니다. 지도 1차 화면은 별도의 `map.html`이며 정답 판정 상태와 구분합니다.

## 지도·서버·외부 접속

지도는 실제 도로 데이터로 만든 공용 그림 지도1개와 문제별 넓은 탐색 범위를 사용합니다. `MAP.quizzes` 순서대로 모든 실제 문제 카드를 세로로 펼치며 카드마다 도착·시연 링크를 제공합니다. `explorationArea`가 있으면 우선하고 없으면 기존 내부 대표 영역을 사용합니다. 지역 탭·가로 문제 전환·정답 위치 핀·GPS 도착 잠금은 없습니다. 자세한 지도 출처·표시 한계는 [지도 안내](map.md)에 있습니다.

‘내 위치 확인’은 사용자의 위치 권한 허용 후 현재 위치와 오차를 한 번 표시합니다. 서버에 전송하거나 저장하지 않습니다. 지도 밖, 큰 오차, 오래된 측정 결과는 안내만 표시하고 부정확한 점을 만들지 않습니다. 실제 현장의 GPS 정확도는 휴대전화에서 추가 확인해야 합니다.

기본 공개 주소는 [GitHub Pages](https://ezid007.github.io/GDG_Incheon/)이며 개발 노트북이 꺼져도 이용할 수 있습니다. [임시 HTTPS 주소](https://machines-ambien-wear-arab.trycloudflare.com/)는 개발 노트북·서버·터널·네트워크가 유지되는 동안의 수정 확인용입니다. 운영과 배포는 [공개 운영 안내](deployment.md)를 따릅니다.

로컬 서버는 `127.0.0.1:4179`에서 `index.html`, `map.html`과 예시 SVG 3개만 GET·HEAD로 제공합니다. 다른 경로는 404이며 문서·로그·환경 변수·첨부 원본 폴더를 제공하지 않습니다. 게임·지도 HTML에는 필요한 사진·SVG·코드가 내장되고 외부 지도 타일을 요청하지 않습니다. GitHub Pages는 배포한 `public/` 파일을 제공하므로 로컬 서버의 경로 제한과 구분합니다.

## 협업과 발표 준비

현장 담당은 장소 찾기 사진·2차 사진·정답 확인 사진의 역할을 구분하고 문제 담당은4개 보기와 근거를 검수합니다. 제작 담당은 모든 카드를 세로로 확인할 수 있는지와 카드별1차 탐색·2차 퀴즈·다음 문제 지도/목록까지 확인합니다. 추가 문제는 검수된 순서대로 같은 세로 목록에 연결하며 사진 역할에 대한 사용자 지시를 우선합니다.

발표에서는 ‘지도와 사진으로 찾아가기 → 현장 관찰 → 정답 근거 확인’을 먼저 설명합니다. 현장에 없는 발표자는 별도 시연 링크로 2차 퀴즈를 보여줄 수 있습니다. 사람과 Agent가 맡은 역할, 현장 관찰을 통해 확인·수정한 내용을 함께 기록합니다.

2차 문제 사진은 `quizImage`·`quizImageAlt`로 지정한다. 게임 본문과 확대 화면의 정답 전 사진은 이 파일을 사용하고, 시작 화면·탐색 지도는 `image`의 부분 사진을 유지한다. `quizImage`가 없으면 기존 방식과 호환되도록 `image`를 사용한다. 두 사진 필드는 대체 설명과 쌍으로 검증하며 빌드에 내장한다.

## 팀원 문제 소스 통합

팀원의 정리 커밋에 따라 `missions.json`은 사용하지 않는다. `load-quiz.mjs`는 `quiz.js`의 질문·선택지·좌표를 읽고 `quiz-support.json`의 검수 정보(단서/문제/정답 사진 설명·해설·근거 좌표·검수 정답)와 결합한다. 팀원 형식의 `correctAnswerIndex`는 1부터 시작하는 보기 번호로 해석하고, 해당 보기의 글자가 검수 정답과 같은지 확인한다. 원본 세 사진과 공개 복사본이 다르거나 새 문제가 아직 검수 목록에 없으면 빌드를 중단한다. 사진 이름만으로 힌트 공개 여부를 결정하지 않는다.
